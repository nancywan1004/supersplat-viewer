# 大场景 LOD 现有管线分析

## 概述

现有大场景 3DGS LOD 管线可以先按 **LOD 语义模型** 分成两类：

- **Chunk\-based（离散档位型）**：把场景切成**空间块**，每个块预先生成 L0～LN 等固定档位。运行时决定「这个块显示哪一档」。Supersplat\-Viewer 与 Aholo Chunk\-LOD 都属于这一类。

- **Splat\-based（树状层级型）**：把 splat 合并成一棵**层级树**。运行时根据**屏幕尺度**决定「父节点是否展开成子节点」。Spark / Tiny\-LOD / Bhatt\-LOD 属于这一类。

三条管线可以概括为：

- **Supersplat\-Viewer**
    - 一句话：先对全场景统一生成多级 LOD，再切成 octree 空间块，由 PlayCanvas 按视角流式加载，viewer 侧优先细化视野中心。
    - 特点：全局简化更一致，跨块画质更连续；代价是调度块是后切出来的，资源粒度、下载/解析/上传和调度参数会更直接影响局部变清速度。
    - 适用场景：当前主线方案，适合中大型展示和亿级场景适配。

- **Aholo Chunk\-LOD**
    - 一句话：先把场景切成空间块，再在每个块内独立生成多级 LOD，运行时直接按块加载、切档和释放。
    - 特点：生成单元、加载单元和释放单元天然一致，便于按块估算粗级基线、细档峰值和释放范围；代价是块与块之间缺少全局联合简化，边界处更容易细节不连续，档位切换也更容易产生跳变。
    - 适用场景：适合作为资产组织和预算表达参考，不作为当前主线替换目标。

- **Splat\-based / Spark**
    - 一句话：把 splat 组织成层级树，运行时按屏幕尺度逐步展开节点。
    - 特点：细化连续、缺页时有父节点兜底；代价是数据页、树遍历和资产组织更复杂。
    - 适用场景：适合强调移动连续性和渐进细化体验的管线，不适合作为当前 viewer 的低成本替换路径。

后续对比主要关注六个指标：**初始加载、由糊变清晰、帧率、内存、GPU 显存、亿级场景加载调度支持**。

## Chunk\-based 与 Splat\-based 的原理对比

### LOD 生成

#### Chunk\-based 生成

Chunk\-based 的产物是「空间块 × LOD 档位」矩阵：

```Plain Text
chunk_0: L0 / L1 / L2 / L3 / L4
chunk_1: L0 / L1 / L2 / L3 / L4
...
```

Supersplat\-Viewer 与 Aholo 都使用 **training\-free** 简化思路，算法为 **NanoGS 渐进式成对合并（MPMM，Mass\-Preserving Moment Matching）**：

##### 分层原理：

1. 先用 **KD 树**在 3D 空间中找出 16 个最近邻作为候选

2. 再对每条候选边计算**合并代价**（几何分布损失 \+ 颜色差异）

3. 然后按代价从低到高**贪心选取互不冲突的配对**，将两个高斯融合为一个

4. 重复多轮直到数量降到目标（如保留 40%）

##### 分块原理：

1. 空间索引：B\-Tree（中位分裂二叉树）

    1. 取合并后所有LOD全部splat质心`(x, y, z)` 建表

    2. 递归构建二叉树：

        1. 在 **最长 AABB 轴** 上用 `quickselect` 找中位数分裂

        2. 叶节点条件：`indices.length <= 256`

    3. `writeLod` 在此树之上 **二次细分**

2. 分块阈值

|参数|CLI 短选项|含义|CLI 默认值|流水线默认值|
|---|---|---|---|---|
|`--lod-chunk-count`|`-C`|每个 chunk 文件的目标高斯数，单位为 **K**（×1024）|512 → **524,288**|96 → **98,304**|
|`--lod-chunk-extent`|`-X`|空间叶子允许的最大边长（**米**）|16|10|

内部换算：

```Plain Text
const binSize = chunkCount * 1024;   *// 单文件高斯上限（约）*
const binDim  = chunkExtent;         *// 单区域最大空间跨度（米）*
```

3. 树节点细分规则

`writeLod` 递归遍历 B\-Tree，对每个节点：

```Plain Text
若（无 indices 且 (count > binSize 或 largestDim > binDim)）:
    → 继续向子节点细分，生成 internal MetaNode（只有 bound + children）
否则:
    → 作为空间叶子，按 LOD 分桶写入 chunk 文件
```

**双重停止条件：**

- **数量约束**：区域内 splat 总数不超过 `binSize`

- **空间约束**：区域 AABB 最长边不超过 `binDim`

任一维度超标即继续向下分裂。B\-Tree 原生叶节点（≤256 splat）因带有 `indices`，会直接走分桶逻辑；更大的内部节点由 `count` / `extent` 控制是否继续切分。

两个管线的差异主要在离线顺序：

- **Supersplat\-Viewer**：先对全场景做 L0 \-\> L1 \-\> \.\.\. \-\> LN 链式简化，再组织成八叉树/块。好处是简化时能看见全局分布，跨块画质更一致；代价是运行时调度块是后切出来的，某个视野区域变清时更依赖资源文件布局和加载调度。

- **Aholo Chunk\-LOD**：先八叉树分块，再对每块生成 L0 \-\> L4。好处是一个块从生成、加载到释放都是同一个调度单元，更容易按块估算首屏粗级基线、细档峰值和释放范围；代价是每块独立简化，跨块边界的一致性弱于全场景先分层。

#### Splat\-based 生成

Splat\-based 生成的是一棵「父 splat 表达子 splat 集合」的树。每个父节点记录自己的子节点起始位置和数量，离线阶段从细节点开始合并，得到更粗的父节点。

##### 分层依据：feature\_size

每个 splat 的 LOD 层级由其 **特征尺度** 决定：

```Plain Text
feature_size = 2.0 × max_scale × lod_opacity
```

- `max_scale`：高斯椭球最大半轴

- `lod_opacity`：由 opacity 推导的 LOD 可见度因子

- 含义：splat 在屏幕上大致占用的可见尺度，越大越应作为父节点（粗粒度）

##### 两种建树算法

|算法|默认参数|合并策略|适用场景|
|---|---|---|---|
|**Tiny\-LOD**|`lod_base = 1.5`（在线）/ 可配|同网格内批量合并，Morton 码排序|快速生成、Worker 在线建树|
|**Bhatt\-LOD**|`lod_base = 1.25`，`MERGE_BASE = 2.0`|26 邻域 \+ Bhattacharyya 相似度，逐对合并|离线预构建（`--quality`）|

###### Tiny\-LOD 分层流程

1. 按 `feature_size` 升序排序

2. 层级循环：`level` 递增，`step = lod_base^level`

3. 收集 `feature_size ≤ step` 的 splat 进入当前层

4. 按 `grid = center / step` 划分 3D 网格，同网格内 Morton 码排序后合并

5. 合并结果作为下一层父节点，迭代至单根

**层级含义**：每一 `level` 对应一个空间步长 `step`，步长指数增长，形成由细到粗的多层结构。

###### Bhatt\-LOD 分层流程

1. 同样按 `feature_size` 排序，用优先队列从大到小处理

2. 在 26 邻域内用 `similarity = bhattacharyya × exp(-color_delta²)` 选最佳合并对象

3. 每次只合并一对，质量更高

4. 后处理 `recurse_to_output`：若父节点 `feature_size ≥ max_child × lod_base` 则保留，否则剪枝

5. `recurse_indices` 按 `limit_size` 逐层展开并重排索引

**与 Tiny\-LOD 的差异**：Bhatt 会**剪枝**冗余内部节点，最终 splat 数小于原始树节点总数（`output_count < splats.len()`）。

##### 树结构

两种算法均生成 **单棵 LOD 树**：

```Plain Text
[根节点 - 整场景最粗表示]
                   /          |          \
            [父节点 A]    [父节点 B]    [父节点 C]
            /    \           |           ...
      [叶子]  [叶子]     [父节点 B1]
                          /    \
                       [叶子]  [叶子]
```

- **根节点**（index 0）：整场景最粗粒度

- **内部节点**：合并后的 splat，带 `children` 指针

- **叶子节点**：原始 splat 或最终保留的细粒度节点

每个节点存储：`center`、`size`（feature\_size）、`child_start`、`child_count`。

### 2\.1 加载与调度

#### 2\.1\.1 Chunk\-based 调度

Chunk\-based 调度目标是让每个空间块从 `currentLevel` 走向 `targetLevel`：

```Plain Text
for each chunk:
  计算视锥、距离、权重与 splatBudget
  得到 targetLevel

flush:
  如果 targetLevel 比 currentLevel 更粗:
    优先卸载或替换，释放预算
  如果 targetLevel 比 currentLevel 更细:
    加载目标资源文件或文件内切片
    等解码、GPU 上传、排序就绪
    新档 ready 后再替换旧档
```

因此 Chunk\-based 的关键瓶颈主要落在 **目标资源是否已加载、下载队列是否被旧视角请求占住、文件落地后是否能及时上屏，以及分块是否过粗或过细**。当前 Supersplat\-Viewer 已经通过中心优先、下载队列门控、旧请求释放和落地后上屏同步缓解了默认流式加载的滞后。更准确的判断是：首次无缓存加载、独立资源文件数量、网络状态、解析上传成本和预算策略共同决定变清速度。

#### 2\.1\.2 Splat\-based 调度

Splat\-based 从树根开始决定节点是否展开：

```Plain Text
queue.push(root)
visible = []

while queue not empty and visible.count < splatBudget:
  node = queue.popMax(pixel_scale)

  if node.child_count == 0:
    visible.add(node)
    continue

  if node.pixel_scale < 1:
    visible.add(node)
    continue

  if children page/range not resident:
    request(node.children.page_or_range)
    visible.add(node)        // 子数据缺失时用父节点兜底
    continue

  for child in nodes[node.child_start .. node.child_start + node.child_count):
    queue.push(child)
```

`pixel_scale` 可以理解为「这个节点投影到屏幕上还有多大」。它通常由三类信息共同决定：

- `feature_size`：节点本身代表的空间尺度或视觉重要性，越大越值得展开。

- 视距与投影参数：离相机越近，投影像素越大，越需要展开。

- `foveate` / 注视区权重：屏幕中心或交互焦点区域会被放大优先级，边缘区域可以更粗。

`pixel_scale < 1` 的含义是：该节点投影小于约 1 像素，继续展开对画面收益有限，可以保留父节点。这个判断比固定 L0～LN 更连续，所以快速移动时更容易显得顺滑。

`SplatPager` 的 GPU 页池可以理解为：Splat\-based 会把大文件切成**固定大小的数据页**，CPU 侧遍历树时发现某个子树需要更细，就请求对应 page 或 byte range；GPU 侧有一个有限大小的 page pool，负责把已取回的数据放进固定槽位。

这里的 **GPU page** 指 GPU 资源池中的一个物理槽位。实现上它可以是大纹理中的一段区域，也可以是 buffer/texture array 中的一页；关键点是「固定容量、可复用、可驱逐」。运行时会维护逻辑 page 到物理 page 的映射，池满时按 LRU 或类似策略驱逐旧 page，再把新 page 上传进去。这样**显存上限比较明确**，调度路径也更依赖从 root / chunk 0 沿树逐步触达子 page。

### 2\.2 优劣势对比

对比主要关注六个指标：**初始加载、由糊变清晰、帧率、内存、GPU 显存、亿级场景加载调度支持**。

- **初始加载**

    - **Spark（Splat\-based）**：先加载头信息、根节点和数据页。优点是较早出画面；问题是首屏偏粗。判断：连续性好，初始清晰度弱。

    - **Supersplat\-Viewer（Chunk\-based / PlayCanvas）**：依赖元数据、首屏门槛、资源文件分布和浏览器缓存状态。南广场首屏约 5\-15 秒，Finland 约 11 秒。判断：已基本符合优化目标；首次无缓存加载仍受独立资源数量和分块粒度影响。

- **由糊变清晰**

    - **Spark**：树状连续展开，缺页有父节点兜底。判断：体感最连续，但数据页和树遍历调度复杂。

    - **Supersplat\-Viewer**：已有中心优先、旧请求释放、稳定待加载统计和落地后上屏同步。南广场由糊变清基本 3 秒内。判断：中型场景变清已可控；亿级粗分块仍会用变清时间换帧率。

- **帧率**

    - **Spark**：**预算驱动 traverse** 把每帧参与调度的 splat 数 capped 在 `maxSplats`；65536 固定页 + Worker 解码也压低单帧 I/O 尖刺。判断：**帧率上限与单帧抖动都较可控**，但 traverse / 页池 / 索引维护实现复杂。

    - **Supersplat\-Viewer**：`splatBudget` 管住上屏点数，WebGPU 把排序热路径挪到 GPU，同预算下渲染吞吐更高。判断：**渲染阶段上限最好**；帧率仍可能被主线程「叶子数 × LOD 评估」、SOG 整包解码与 work buffer 写入拉扯，且依赖 WebGPU 支持与显存预算。

- **内存**

    - **Spark**：65536 固定页 + 页池 LRU 决定 CPU / GPU 驻留；多数细化只改 indices，不必整文件换入。判断：**峰值模型统一、可预期**，但页池容量与驱逐策略内聚在引擎侧，业务侧难精细调参。

    - **Supersplat\-Viewer**：按 `(chunk × LOD 级)` 独立 SOG 驻留；关键资源保护、待加载队列、旧请求释放、LOD 范围均可配置。判断：**常驻与 transient 边界清楚**，产品与运维侧可控性强。

- **GPU 显存**

    - **Spark**：GPU 页池硬上限，逻辑页映射到固定物理槽位；命中则展开细档，未命中则父节点兜底。判断：**显存峰值清楚**，近景画质依赖页池命中率与 fetch 速度。

    - **Supersplat\-Viewer**：splat 纹理 + WebGPU 排序 / compute buffer；资源共享使多实例不随理论总点数线性叠加。Poland 单体约 178\-298MB，x5 多数约 202\-250MB。判断：**共享资源下峰值可控**；细档上屏与 WebGPU 路径会抬排序缓冲占用，多区域 / 多资产仍需控峰值。

- **亿级场景加载调度支持**

    - **Spark**：显存池清楚，traverse 预算驱动、不随场景总节点数线性增长。判断：适合控显存与快速移动，但索引和遍历实现复杂。

    - **Supersplat\-Viewer**：PlayCanvas 2\.20 + 资源共享 + 实例级 LOD 范围。Poland 1\.04 亿点及 x5 / x10 可保持 60 帧左右。判断：规模扩展和帧率可控，但 **CPU 调度成本随 octree 叶子数上升**；下一步重点是分块、上屏点数、变清时间三者平衡。

**典型场景（约 100M splats，相机快速前移）**：

| 阶段 | PlayCanvas（Supersplat\-Viewer） | Spark |
| --- | --- | --- |
| **调度** | 遍历八叉树可见叶子，逐个算距离选 LOD | 从根展开，到 `maxSplats` 停止 |
| **跨 LOD** | 多片叶子同时跨阈值 → 批量请求新 SOG | `touched chunks` 追加 fetch，**父节点先顶着** |
| **单帧尖刺** | 大 chunk WebP 解码 + work buffer 写入 | 65536 上限 + Worker decode |
| **CPU** | 叶子数 × LOD 评估（主线程） | WASM Worker traverse，且有 **dirty 门控** |

**根因与综合判断**：

PlayCanvas / Chunk\-based 调度受节点数制约，主要因为：

- 每帧 CPU 遍历空间树，成本随**叶子数**增长；
- LOD 是**离散换档**，每个 `(叶子, LOD 级)` 是独立数据包；
- **空间粒度 = 加载粒度**：分块越细则 CPU 调度越重，分块越粗则 I/O / 解码越重；
- SOG + work buffer 使每次加载都是「整包解码 + GPU 灌入」，**块越大尖刺越明显**。

Spark / Splat\-based 能扛更大规模，核心**不是 traverse 算得更快**，而是：

- **加载单位固定（65536）**，与空间树解耦；
- **换细节 ≠ 换文件**，多数展开只改 indices；
- **有界页池 + 父节点降级**，避免「等整块到了才能渲染」；
- **预算驱动 traverse**，不随场景总节点数线性增长。

据此：

- Spark 更适合强调**移动连续性**、缺页兜底和快速前移下的调度稳定；

- Supersplat\-Viewer 更适合强调 **WebGPU 渲染上限**和**中心优先细化**；后续重点是在现有架构内收敛分块粒度、LOD 范围、上屏点数和下载优先级，并缓解「叶子数 × 离散换档 × 整包解码」叠加带来的 CPU 与尖刺问题。

### 2\.3 Supersplat\-Viewer 可引入的优化点

在不改变现有 Chunk\-based 架构的前提下，Supersplat\-Viewer 更适合优先收敛以下优化：

- **分块参数**：比较粗 / 中 / 细分块。看上屏点数、**节点数**、帧率、内存、显存，不只看变清时间。空间粒度即加载粒度——过细放大 CPU 调度与叶子评估，过粗放大 SOG 整包解码与 work buffer 写入尖刺；需在「调度成本」与「I/O / 解码成本」之间找平衡。

- **中心优先细化收敛**：优先细化激进程度分高 / 中 / 低。高档下载更积极、中心区域优先排队，全量扫描频率更高；低档下载更克制，并发更低，全量重扫频率更低。目标之一是减少「遍历全部可见叶子 × LOD 评估」的主线程压力，借鉴 Spark 的 **dirty 门控**：相机 / 视锥变化不大时跳过全量重算；细档 SOG 未 ready 时保留当前粗档上屏（对标 Spark「子页未 resident 则父节点先顶着」），缩小离散换档与整包解码带来的空档。

- **亿级上屏点数控制**：上屏点数、LOD 范围、帧率、显存作为主控指标。用预算截断调度深度，避免调度成本随场景规模线性膨胀。

**Splat\-based 思路中适合补充到 Chunk\-based 的部分**：

- **资源驻留状态**：记录每个资源文件 / 分块的已驻留、加载中、可释放状态，辅助判断慢在下载、上传、缓存命中还是释放策略；对标 Spark 有界页池的可观测性。

- **预算压力下的释放优先级**：参考 page pool 的驻留管理思路，在调度器中优先释放低权重、出视锥、可重建成本低的资源；池满时不应阻塞细化，而应可预测地腾挪槽位。

- **屏幕像素误差选级**：引入类似 `pixel_scale` 的屏幕投影指标，让「是否继续变清」更贴近可见收益，而不是只按距离和固定预算决定；减少无效 `(叶子, LOD 级)` 换档请求。

## 渲染路径、WebGPU 支持与设备约束

LOD 只决定加载多少、显示多细；帧率还取决于排序、光栅化、分辨率和渲染后端。对比指标必须标注设备、浏览器、WebGL/WebGPU 模式和预算参数。

### WebGPU 相比纯 WebGL 的优势

- **Supersplat\-Viewer / PlayCanvas：有 WebGPU 加速路径**。主要用于把排序等高 splat 数热路径转到 GPU，降低 CPU 排序瓶颈；实验性 compute 路径还可进一步减少全局排序压力。代价是排序 buffer、compute buffer 和显存占用更高，且依赖浏览器 WebGPU 支持。

- **Aholo 当前正式 Splatting 路径：没有通过 WebGPU 加速 3DGS 热路径**。EGS 有 WebGPU 后端，但当前 Viewer 的 splatting 仍以 WebGL2 和排序 preset 为主，帧率优化主要靠 `maxBudget`、调度限流和渲染 preset。

- **Spark 生产路径：没有把 WebGPU 作为主要帧率开关**。它的核心优化在 LOD 树遍历、输出 splat 数控制和 `SplatPager` 显存池。

相比纯 WebGL 管线，WebGPU 的优势主要体现在高 splat 数上屏后的渲染阶段：

- **排序压力从 CPU 转向 GPU**：纯 WebGL 路径更容易在大量 splat 排序时占用 CPU 和主线程；WebGPU GPU 排序能降低 CPU 排序瓶颈，减少相机移动或细档上屏后的帧率抖动。

- **同等上屏预算下帧率更稳**：Supersplat\-Viewer 也有 `splatBudget`，但 WebGPU 改变的是预算内 splat 的排序/渲染执行路径。同样预算下，WebGPU 更容易保持稳定帧率；设备足够强时，也更有机会承载更高上屏预算。

- **更适合高密度细档上屏**：当 LOD 已经把近景推到 L0/L1，瓶颈会从加载调度转向排序和绘制。WebGPU 的收益主要出现在这个阶段，而不是 meta 下载、SOG 解码或粗到细调度阶段。

- **代价是显存和兼容性**：WebGPU 排序/compute buffer 会增加 GPU 显存压力；设备、驱动和浏览器支持差异也更明显。因此 WebGPU 应作为 Supersplat\-Viewer 的**渲染上限能力**，而不是加载优化手段。

## 后续优化方案

目标不变：在现有架构内收敛四个问题：

- 首屏是否稳定。
- 由糊变清是否快。
- 帧率 / 内存 / 显存是否可控。
- 亿级场景是否能 scale。

不做整体架构调整，重点只放在：分块参数、细化调度参数、LOD 范围 / 上屏点数预算、评测口径。

### 当前状态判断

**已基本符合优化目标：**

- **PlayCanvas 2\.20 流式 LOD 基础能力**：加载调度与渲染解耦、LOD 补跑、多实例资源共享、实例级 LOD 范围已经支撑当前主线。
- **中型大场景中心变清**：南广场 4089\.2 万点已能做到正常网速下约 3 秒内由糊变清，具备汇报价值。
- **亿级场景帧率控制**：Poland 1\.04 亿点及多实例复制场景可保持约 60 帧，说明上屏点数受控时规模扩展可行。
- **viewer 侧细化调度**：中心优先、旧请求释放、落地后上屏同步已明显缓解默认流式加载的滞后。

**仍需进一步优化：**

- **分块参数**：Finland 5518\.3 万点帧率偏低，说明分块过细、节点过多会放大调度和渲染成本。
- **亿级变清速度**：Poland 粗分块能稳帧，但部分关键帧由糊变清仍在 10\-30 秒量级，需要压缩等待时间。
- **多区域预算**：多区域 / 多资产同时细化时，仍需要更明确的上屏点数、LOD 范围和显存上限。
- **评测口径**：需要稳定区分慢在下载、解析、上屏同步、预算抖动还是渲染瓶颈。

### 4\.1 优化原则

- `performanceFirst`：先稳帧率、内存、显存。

- `qualityFirst`：先保近景细节和停住后变清速度。

- 3000\-5000 万级：可偏 `qualityFirst`，突出中心 3\-5 秒内变清。

- 亿级：优先 `performanceFirst`，先压上屏点数、帧率、显存。

- WebGPU 是渲染上限，不是加载优化；后续重点仍是分块、LOD 范围、上屏点数、调度参数。

### 4\.2 performanceFirst 优化方向

目标：稳帧率、稳内存、稳显存。

- **P0：上屏点数预算控制**

    - 做法：上屏点数、帧率、显存、LOD 范围联合看。
    - 作用：控制每帧上屏规模。
    - 代价：远处或新触达区域变清更慢。

- **P0：分块参数 A/B**

    - 做法：粗 / 中 / 细三档对比。
    - 作用：找帧率与变清时间平衡点。
    - 代价：需要多轮资产构建和评测。

- **P0：保守预算与并发上限**

    - 做法：降低上屏点数、下载并发、上传峰值；非重点区延后细化。
    - 作用：控制帧率抖动和显存峰值。
    - 代价：近景恢复更慢。

- **P1：现有细化参数收敛**

    - 做法：收敛中心优先、前景 / 关键区域范围、旧请求释放、待加载统计、上屏同步。
    - 作用：减少旧请求占用下载通道和外围抢带宽。
    - 代价：参数过激会抖，过保守会慢。

- **P2：多区域参与度控制**

    - 做法：限制同时细化的区域数量。
    - 作用：避免多区域 / 多资产峰值叠加。
    - 代价：跨区域快速移动时可能短暂粗糊。

### 4\.3 qualityFirst 优化方向

目标：提高近景细节和停住后的变清速度。

- **P0：更高细档预算**

    - 做法：提高近景预算，降低中心区域惩罚权重。
    - 作用：中心和近景更快触达细档。
    - 代价：显存、排序、绘制压力更高。

- **P1：近距跳档**

    - 做法：近距节点更快追细档。
    - 作用：减少中间档等待。
    - 代价：单轮下载、解码、上传峰值更高。

- **P1：屏幕像素误差选级**

    - 做法：用屏幕投影大小参与目标档判断。
    - 作用：减少不可见收益低的细化。
    - 代价：需要与距离 / 预算规则调和。

- **P1：首屏后短时高并发**

    - 做法：首屏完成后短时间提高前景 / 关键区域加载上限。
    - 作用：首波变清更快。
    - 代价：需控制 CPU / GPU 峰值。

### 4\.4 筛选后的优先级

当前优先级：

- **P0：统一评测口径**：固定记录点数、文件数、叶子节点数、分块参数、缓存状态、WebGL/WebGPU、上屏点数、帧率、内存、显存、由糊变清时间。

- **P0：分块参数 A/B**：Finland 找帧率与变清平衡点；Poland 保留稳帧路线，同时尝试压缩 10\-30 秒变清。

- **P1：细化调度收敛**：优化中心优先、旧请求释放、待加载判定、上屏同步时机。

- **P1：亿级预算控制**：用上屏点数、LOD 范围、帧率、显存控制多区域细化。

- **P2：轻量资产实验**：验证合并资源包 / 更小分块；打包资源、代理合并、常驻粗级暂不进主线。

## 最终总结

Chunk\-based 与 Splat\-based 的根本差异是运行时选择单位：

- Chunk\-based：选「空间块的固定档位」。优势是生成、缓存、卸载直观。
- Splat\-based：选「树节点是否展开」。优势是连续性好，缺页有父节点兜底。

当前判断：

- 不换现有 Supersplat\-Viewer 架构。
- Aholo 作为资产组织和预算解释参考。
- 优先收敛分块参数、细化调度、上屏点数预算、评测口径。

汇报结论：

- 3000\-5000 万级：已能做到较快中心变清和较稳帧率。
- 亿级：可以扩展，但必须控制上屏点数、LOD 范围、分块粒度、显存峰值。
- 下一步：不是换管线，而是把现有管线参数调稳、指标讲清。
