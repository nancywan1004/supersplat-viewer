## 场景选中与输入分层说明

本文说明 Viewer 内「场景资产选中」与「灯光选中」的交互差异，并梳理与 `input-controller` / `picker` 的分层关系，便于后续扩展和重构时保持一致的架构思路。

---

### 1. 分层概览

- **底层输入层：`input-controller.ts`**
  - 统一接管键盘、鼠标、触摸、手柄等原始输入事件。
  - 负责：
    - 生成相机控制用的 `InputFrame`（move/rotate）。
    - 识别「双击 / 双指 tap」等高阶手势，派发 `events.fire('inputEvent', 'dblclick', event)` 等。
    - 在画布上单击时，基于 `pickWorldFromClientXY` 计算世界坐标，并派发**通用的「世界点击」事件**：`scenePointerWorldClick`（payload 当前为 `Vec3` 世界坐标）。
  - 不关心具体业务（选资产 / 选灯光 / 放注释 / Bloom 画笔），只负责产出「语义化输入」：相机增量、世界坐标、基础手势。

- **坐标转换与深度拾取：`picker.ts`**
  - `class Picker`：基于 PlayCanvas `PcPicker(depth=true)` 和 `World` layer，支持在 [0,1] 归一化坐标下读取深度并反投影为世界坐标。
  - `pickWorldFromClientXY(global, clientX, clientY): Promise<Vec3 | null>`：
    - 对外统一封装从浏览器事件坐标 `clientX/clientY` → 世界坐标的流程：
      1. `canvas.getBoundingClientRect()` 计算点击在画布内的归一化坐标 \([0,1]\)。
      2. 内部维护并复用单个 `Picker` 实例（挂在 `global.__picker`），避免各处重复创建与尺寸管理。
      3. 调用 `Picker.pick(nx, ny)`，返回 `Vec3 | null`。
    - 所有需要「屏幕点击 → 世界坐标」的模块（资产、灯光、注释、Bloom 画笔等）都应优先通过此方法获取世界坐标，避免重复实现 rect 计算和 `PcPicker` 封装。

- **上层业务模块：**
  - **资产编辑**：`asset-placement-handler.ts` + 资产列表 / Gizmo。
  - **灯光编辑（环境模块）**：`light.ts` + `lighting-ui.ts` + 环境底部工具栏 + Gizmo。
  - **标注放置**：`annotation-toolbar/placement-mode.ts`。
  - **Bloom 局部亮度画笔**：`vfx/bloom.ts`。
  - 这些模块：
    - 统一从 `pickWorldFromClientXY` 或 `input-controller` 产出的世界坐标/事件中取输入；
    - 再根据各自的业务语义，更新 `global.state`、操作实体 / Gizmo、发协议消息等。

### 2. 场景资产选中 vs 灯光选中：交互与命中逻辑

#### 2.1 输入手势上的差异（但目标是一致的）

- **资产选中**
  - 用户期望：和常规 3D 编辑器一致——**单击选中资产，双击镜头对焦**。
  - 实现（高层抽象）：
    - 单击：由资产模块监听「世界点击」事件或 raycast 结果，决定当前选中资产。
    - 双击：`camera-manager.ts` 监听 `events.on('pick', worldPos)`，根据拾取位置进行相机 framing。

- **灯光选中**
  - 交互目标与资产对齐：**单击选中灯光，双击仍用于相机 framing**。
  - 实现（我们这轮改造的部分）：
    1. `input-controller.ts` 在画布 `pointerup`（主指针、左键、落在画布内）时，通过 `pickWorldFromClientXY` 计算一次世界坐标。
    2. 命中时触发当前的 `events.fire('lightPick', worldPos)`（后续建议重命名为 `scenePointerWorldClick` 等中性名字）。
    3. `camera-manager.ts` 监听旧有的 `pick`（双击）仅做相机 framing；  
       `light.ts`（或相关模块）监听「世界点击」事件，通过空间最近灯光逻辑完成灯光选中。

> 总体目标：  
> - 手势层：资产和灯光都以**单击选中、双击 frame**为统一交互；  
> - 输入层：由 `input-controller` 输出统一的「世界点击」事件 + 「双击 pick」事件；  
> - 业务层按需监听并解释这些输入。

#### 2.2 命中目标上的差异

- **资产选中：按类型的几何 / ID 拾取**
  - **Mesh / image / video 等**：`asset-placement-handler` 经 `input-arbiter` 使用 **`pc.Picker(depth=false)`** + `getSelectionAsync`（World 层，5×5 邻域过滤已放置列表）。
  - **已放置 unified 高斯**：主场景 World 层合成 pick 会盖住 placement 的 `vPickId`；改为 **`SceneAssetPick` 层** 单独 ID 拾取 + 必要时深度/AABB 兜底（`scene-asset-selection-pick.ts`）。详见 [场景拾取与Picker双路径说明.md](场景拾取与Picker双路径说明.md)。
  - 目标对象是「有几何形状并参与渲染的实体」，选中行为基于**可见几何或放置层 ID**。

- **灯光选中：基于空间距离的语义选中**
  - 当前逻辑在 `light.ts` 中，通过 `selectNearestLightAtPosition(global, position: Vec3)` 实现：
    - 遍历所有点光 / 聚光的可视化实体（球体 / 锥体），读取其世界位置。
    - 计算点击位置到每个灯光的距离，选择最近的一个（在一定半径阈值内，例如 2.5 米）。
    - 更新 `state.selectedLightId`，并触发 `events.fire('sceneLight:selected', { id })`。
  - 特点：
    - **不要求 ray 真正“命中”灯光的可视化 mesh**——即便可视化实体很小或部分被遮挡，只要点击点附近最近的就是它。
    - 更偏向语义上的“我点的是这个区域的灯光”，而不是精确的三角形命中。

### 3. 状态与 UI / Gizmo 联动上的差异

#### 3.1 资产选中路径

- 状态字段（示意）：`state.selectedSceneEntityId` 等。
- 主要联动：
  - 左侧/资产列表的选中高亮。
  - Transform Gizmo：使用 `assetTransformMode`（move/rotate/scale），挂在被选中的资产实体上。
  - `message-bridge` 协议：`ASSET_SELECT` / `SCENE_ASSET_SELECTED` 等，用于与宿主应用同步。

#### 3.2 灯光选中路径

- 状态字段（本轮改造新增/强化）：
  - `state.selectedLightId`：当前选中的光源 ID。
  - `state.lightTransformMode`：当前灯光的 Gizmo 变换模式（'move' | 'rotate'）。
- 主要联动：
  - 右侧 `Lighting` 列表：
    - 根据 `selectedLightId` 高亮对应行（`pointLightRow--selected`）。
    - 列表点击行时更新 `selectedLightId` 并触发 `sceneLight:selected`，实现列表 ↔ 场景双向联动。
  - 环境模块底部工具栏：
    - 按钮「移动 / 旋转 / 编辑 / 删除」根据 `selectedLightId` / `lightTransformMode` 更新激活态与禁用态。
    - 通过 `lightTransformMode:changed` 驱动 Gizmo 的切换。
  - Transform Gizmo：
    - `gizmo-handler.ts` 在 `state.editLeftModule === 'environment'` 时，使用 `selectedLightId + lightTransformMode` 决定 Gizmo 附着到哪个灯光实体、以何种模式（平移/旋转）工作。
    - pointer:up 时，将灯光新的 `position / pitch / yaw` 回写到 `settings.lighting.lights`，并通过 `updatePointLightsFromSettings` 与 `pushEditHistory('transform light')` 持久化与可撤销。
  - `message-bridge` 协议：
    - `LIGHT_SELECT` / `LIGHT_ADD` / `LIGHT_DELETE` / `SCENE_LIGHT_SELECTED` 等，与宿主应用在光照模块上的编辑保持同步。

> 虽然「选资产」与「选灯光」整体流程非常相似（都是“选中 → 列表/工具栏高亮 → Gizmo → 协议同步”），  
> 但通过不同的 state 字段和 UI 区域（资产模块 vs 环境模块）实现解耦，避免在编辑不同模块时互相干扰。

### 4. 标注与 Bloom 为何不直接监听 `lightPick`

#### 4.1 标注放置：`annotation-toolbar/placement-mode.ts`

- `PlacementMode` 是一个**输入模式**：
  - 激活时：禁用相机控制、改变光标样式、在 canvas 上监听 `click`，等待用户点击放置占位标注。
  - 结束时：移除监听、恢复相机控制、发出 `annotationPlacement:ended` 等通知。
- 它需要：
  - 明确「当前处于标注放置模式」的状态机；
  - 直接控制自己何时接管/释放 canvas 点击；
  - 对每一次点击调用 `pickWorldFromClientXY`，再发 `annotation:place` 事件。
- 若改为被动监听 `lightPick`：
  - `input-controller` 必须知道当前是否处于注释放置模式，否则无法判断哪些点击应该路由给标注；
  - 或者仍然需要在高层做一层复杂状态过滤，并不比当前“直接在 `PlacementMode` 里监听 canvas + 用通用 picker 封装”更清晰。
- 因此目前方案是：
  - **统一通过 `pickWorldFromClientXY` 共享坐标转换与 `Picker` 逻辑**；
  - 标注自身保留对 canvas 的监听和模式切换逻辑（职责是“注释交互模式管理”而非“一般场景点击”）。

#### 4.2 Bloom 世界空间画笔：`vfx/bloom.ts`

- Bloom 画笔需要完整的 pointer 手势流：
  - `pointerdown`：开始绘制，进入 `isDrawing = true` 状态。
  - `pointermove`：在拖动过程中不断采样 pointer 位置，更新 3D 体素点（`worldSpaceData`）。
  - `pointerup`：结束绘制，触发一次体积重建与 `postEffect:changed`。
  - 需要在 `capture: true` 阶段阻止事件冒泡，避免相机在绘制过程中被误操作。
- 这类需求超出了「单击 worldPos 一次」的粒度，因此：
  - 单纯监听 `lightPick` 这一类 click 事件无法满足拖拽笔刷的连续输入。
  - 让 `input-controller` 为 Bloom 专门抽象一整套 pointer 手势会使底层输入强绑定某个特效，破坏模块解耦。
- 当前方案：
  - Bloom 自己在 `document` 上注册 `pointerdown/move/up`（capture 模式），按需拦截事件；
  - 在需要将 pointer 坐标投射到 3D 时，统一调用 `pickWorldFromClientXY(global, clientX, clientY)`；
  - 这样既复用了坐标/Picker 的公共逻辑，又保持 Bloom 作为一个独立特效模块的输入模式控制能力。

### 5. 事件命名建议与后续演进

目前 `input-controller.ts` 中用于光源选中的单击事件命名为 `lightPick`，但从职责和分层来看，它更接近一个通用的「场景世界点击」事件。建议未来重构时：

1. 将事件从：
   - `events.fire('lightPick', worldPos);`
   改为更中性的命名，例如：
   - `events.fire('scenePointerWorldClick', { position: worldPos, originalEvent: pointerEvent });`
2. 在上层模块中分别监听并解释：
   - **资产模块**：监听 `scenePointerWorldClick`，决定选哪一个资产实体（几何命中或最近资产策略）。
   - **灯光模块**：监听 `scenePointerWorldClick`，调用 `selectNearestLightAtPosition` 完成灯光选中。
3. 保持：
   - `events.on('pick', worldPos)` 继续用于双击 frame 相机；
   - Bloom / 标注等需要完整手势流的模块继续使用自己的 pointer 监听，只在需要坐标转换时调用 `pickWorldFromClientXY`。

通过上述约定，可以在不牺牲模块解耦的前提下，让场景中资产与灯光的选中交互在：

- **手势层**（单击选中 / 双击 frame）、  
- **输入抽象层**（统一的世界点击事件 + 二次封装好的 `pickWorldFromClientXY`）、  
- **业务层**（资产 vs 灯光不同的命中和状态联动策略）

三者之间形成清晰且可扩展的一致性。
