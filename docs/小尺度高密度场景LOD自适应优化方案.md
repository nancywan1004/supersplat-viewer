# 小尺度高密度场景 LOD 自适应优化方案

## 1. 分析范围

本分析不运行场景，只使用：

- 当前查看器与 PlayCanvas 2.20 的层级选择、预算平衡、下载调度代码。
- Poland、jinanqiao-v3-x10、Wuhan、nanguangchang-v6 的原始 `lod-meta.json`。
- 仓库中已有的旧 Poland 96k / jinanqiao 调度日志；这些日志只用于验证通用代码链路，不作为 Poland-new 的性能数据。
- 所有产品行为统一按 `quality mode` 理解。

## 2. 结论

叶节点尺度确实有关，但不是单独通过“叶节点小”产生问题。当前小尺度场景大量 `pending` 的主链路是：

1. 查看器使用固定的 5、15、45、135 米等距离门槛计算未经预算修正的目标层级。
2. Wuhan 和南广场尺度小，大量可见节点在这个绝对米制规则下被判断为需要较细层级。
3. 自定义下载调度器按这个原始目标请求文件。
4. PlayCanvas 随后还会根据点数预算调整基础距离，并通过预算平衡器把部分节点降到更粗层级。
5. 因此调度器可能下载引擎最终不会立即显示的细档文件。
6. 每次移动超过 3 厘米都会立即重新扫描，并清空当前跟踪和固定集合；移动爆发期间引擎更新距离还会被设为 0。
7. 连续小幅移动会反复更换文件优先级，把旧请求放入暂停队列，并产生网络请求尾部。

Poland 和 jinanqiao-v3-x10 的世界坐标尺度大，固定 5 米门槛相对场景很小，未经预算修正的目标本来就较粗，因此下载目标与引擎最终目标之间的偏差较小。

`jinanqiao-v3-x10` 的“放大 10 倍”尤其能证明这个尺度效应：在几何结构相同的假设下，把坐标放大 10 倍，等价于把原始场景中的基础层级距离从 5 米缩小到 0.5 米，更容易选择粗层级。

## 3. 四场景静态对照

| 指标 | Poland-new | jinanqiao-v3-x10 | Wuhan | nanguangchang-v6 |
|---|---:|---:|---:|---:|
| 场景对角线 | 4372 m | 3515 m | 321 m | 593 m |
| `5m / 场景对角线` | 0.11% | 0.14% | 1.56% | 0.84% |
| 精度层数 | 10 | 9 | 8 | 6 |
| 叶节点数 | 32,756 | 80,596 | 1,495 | 11,612 |
| 叶节点尺寸中位数 | 37.3 m | 13.0 m | 8.5 m | 10.0 m |
| 最高精度单叶点数中位数 | 3,259 | 140 | 1,137 | 297 |
| 最高精度文件数 | 1,066 | 1,640 | 170 | 365 |
| 最高精度单文件点数中位数 | 99,892 | 107,532 | 109,653 | 113,797 |
| 最高精度单文件所含叶节点联合包围盒对角线中位数 | 223 m | 36.7 m | 11.3 m | 28.2 m |
| 最高精度单文件关联叶节点中位数 | 31 | 11 | 3 | 8 |

这里的 Poland 来源是用户指定的 `.../LOD/poland-new/lod-meta.json`，生成器为 `splat-transform v3.0.0`。元数据没有直接保存 `minChunkPoints` 的配置值，但其叶节点点数集中在约 3.2K，结构上符合最小叶点数限制后的结果。

### 3.1 单个文件大小不是主因

四个场景最高精度单文件都在约 10 万点。Wuhan 出现 20 个 `pending`，意味着调度器可能同时追约 200 万点对应的文件；网络自然会成为模糊恢复的决定因素。

### 3.2 Poland-new 单文件关联 31 个叶节点是正常打包结果

Poland-new 最高精度叶节点均值约 3,250 点、中位数约 3,259 点；物理文件目标约为 100K 点。于是：

```text
99,892 点 / 约 3,250 点每叶 ≈ 30.7 个叶节点每文件
```

实际中位数为 31，90% 分位数为 33，最大值为 38，与这个估算高度一致。因此它不是元数据损坏，而是“约 3.2K 的逻辑叶节点打包进约 100K 的物理文件”的预期结果。

这对网络请求数量有利：约 31 个逻辑叶节点共享一个物理文件，多个叶节点切档仍可能命中同一个已加载文件。打包顺序通常具有空间局部性，但联合包围盒不能证明所有叶节点连续相邻。与旧 Poland 96k 每文件数百个区间相比，31 个区间对工作缓冲区也更可控。

联合包围盒对角线不能直接当作连续覆盖半径。一个文件中的叶节点可能有间隙，220 米只表示这些叶节点的联合外包范围。移动阈值不能直接使用这个数值；应该计算小幅虚拟位移前后的目标文件集合交集，或使用当前可见叶节点投影尺度。

## 4. 代码放大链路

### 4.1 3 厘米就触发一次完整调度

`bootstrap.ts` 当前条件：

```ts
const moved = streamLastCamPos.distance(camPos) > 0.03;
```

旋转门槛约为 10 度，但平移门槛只有 3 厘米。触发后会立即调用 `notifyCameraMoved()`。

### 4.2 每次通知都会清掉跨帧复用状态

`notifyCameraMoved()` 当前会：

- 将移动爆发窗口重置为 18 帧。
- 清空 `tracked`。
- 清空 `pinned`。
- 清空上一轮优先地址。
- 立即执行一次 `runPriorityPrefetch()`。

`trackedMissFrames` 原本可以让文件在短暂离开优先集合后保留若干帧，但移动通知直接清空了它，等于绕过了这套迟滞机制。

普通平移不会清空暂停队列。新旧视角优先文件不同后，旧请求会进入 `__refinementSuspendedQueue`，连续移动可能持续扩大这个队列。

### 4.3 移动爆发期间引擎更新距离被压到 0

移动后 18 帧内：

```ts
gsplatScene.lodUpdateDistance = 0;
```

这会让引擎对每个微小相机位移重新执行层级预算和应用。已有旧 Poland 96k / jinan 日志已经表明：

- 完全关闭爆发窗口会更差。
- 保留爆发窗口、但不把更新距离压到 0，能减少部分尖峰。

因此应该保留爆发机制，但使用自适应非零距离。

### 4.4 下载调度没有使用预算后的真实目标

自定义调度器计算：

```ts
rawOptimalLod = computeOptimalLodIndex(
    distance,
    lodBaseDistance,
    lodMultiplier
);
```

虽然代码读取了：

```ts
engineOptimalLod = nodeInfo.optimalLod;
```

但它只用于统计不一致数量，没有参与下载目标选择。

PlayCanvas 引擎的实际路径还会执行：

1. 使用 `_budgetScale` 调整有效基础距离和倍率。
2. 统计所有节点目标点数。
3. 使用预算平衡器在远近节点之间升降层级。
4. 把预算后的结果写回 `nodeInfo.optimalLod`。

因此：

```text
自定义下载目标 != 引擎最终显示目标
```

这个偏差在小尺度场景更大，因为原始米制规则会先把更多节点判断为细档。

### 4.5 前景窗口会把偏差直接变成 pending

调度器对候选文件去重后，最多保留 64 个前景文件、8 个核心文件。`pending` 显示的是前景缺失唯一文件数，不是叶节点数。

Wuhan 移动后出现 20 至 27 个 `pending`，代表下载目标集合确实包含 20 至 27 个不同文件，而不是界面统计错误。

## 5. 优化方案

## 5.1 第一优先级：下载目标服从引擎预算结果

这是收益最高、最不影响最终画质的修改。

对每个节点同时保留：

```ts
const rawOptimalLod = computeOptimalLodIndex(...);
const budgetOptimalLod = nodeInfo?.optimalLod ?? -1;

// 层级编号越大越粗。下载器不得追比引擎预算目标更细的文件。
const downloadOptimalLod = budgetOptimalLod >= 0
    ? Math.max(rawOptimalLod, budgetOptimalLod)
    : rawOptimalLod;
```

然后将 `downloadOptimalLod` 传入逐级细化逻辑。

移动后的第一次扫描中，`nodeInfo.optimalLod` 可能仍属于上一相机位置。使用两阶段更新：

1. 相机移动后先请求一次引擎层级更新。
2. 当前帧只保留旧视角和新视角的文件交集，不立即追新的细档。
3. 引擎完成预算更新后，再根据新的 `nodeInfo.optimalLod` 建立下载队列。

即便短暂使用旧的预算目标，`Math.max()` 也只会让下载保守一帧，不会提前下载过细文件。相机停止后仍会按引擎最终质量收敛。

建议增加指标：

- `rawTargetUniqueFiles`
- `budgetTargetUniqueFiles`
- `suppressedOverfetchFiles`
- `rawVsBudgetLodMismatchNodes`

验收重点不是把 `pending` 强行变成 0，而是确认被抑制的文件确实没有进入引擎预算后的目标集合。

## 5.2 第二优先级：区分小幅移动和大幅跳转

不要再让所有超过 3 厘米的移动执行相同重置。

建议按上一轮高优先级可见叶节点的尺度中位数 `visibleLeafScale` 和代表性可见深度计算：

```text
softMoveThreshold =
    clamp(visibleLeafScale × 2%, 0.08 m, 0.40 m)

hardMoveThreshold =
    clamp(visibleLeafScale × 25%, 1.0 m, 8.0 m)
```

再使用代表性可见深度限制屏幕视差，避免近距离大叶节点允许过大的移动。若还没有可见统计，使用采样叶节点尺寸作为启动回退值：

```text
fallbackSoftThreshold =
    clamp(sampledLeafMedian × 2%, 0.08 m, 0.40 m)
```

行为分级：

| 移动类型 | 行为 |
|---|---|
| 小于软门槛 | 不扫描，只累计位移 |
| 超过软门槛 | 更新优先级，但保留 `tracked`、`pinned` 和新旧集合交集 |
| 超过硬门槛、明显缩放或跳转 | 清理旧视角状态，重新建立队列 |
| 相机静止 120–180 ms | 强制执行一次最终质量扫描 |

旋转应继续单独累计，不能和平移共用米制阈值。

## 5.3 第三优先级：保留爆发窗口，但禁止距离归零

将：

```ts
burstUpdateDistance: 0
```

改为运行时值：

```text
burstUpdateDistance =
    max(softMoveThreshold, 0.12 m)
```

这样相机移动时仍会快速响应，但不会因每帧几厘米变化反复执行预算平衡和区间应用。

建议每 80–120 毫秒最多执行一次移动中扫描；静止后再执行最终扫描。

## 5.4 第四优先级：小幅移动不清空复用状态

软移动时：

- 不调用 `tracked.clear()`。
- 不调用 `pinned.clear()`。
- 保留新旧前景文件交集。
- 让 `trackedMissFrames` 自然淘汰连续若干帧不再需要的文件。
- 对暂停队列增加数量上限和存活时间。

硬跳转时才清空。

建议暂停队列：

```text
最大 64 个文件
或最大估算 64 MB 压缩数据
存活时间 1.5–2 秒
```

超过限制优先删除低分、未进入引擎预算目标、未绑定上屏区间的文件。

## 5.5 第五优先级：按“画质收益 / 下载成本”排序

当前文件分数主要来自节点位置、视口中心权重和目标层级，没有计算一个文件能改善多少节点。

建议聚合到文件级：

```text
文件收益 =
    所有关联可见节点的投影误差改善量之和

文件成本 =
    该文件点数
    或已知的压缩字节数

最终优先级 =
    文件收益 / 文件成本
```

四个场景的文件点数接近时，这会优先下载能同时改善更多屏幕区域的文件，避免先下载只改善少量边缘叶节点的文件。

## 5.6 第六优先级：空闲时做很小的方向性预取

Wuhan 高精度文件空间范围中位数只有 11.3 米，文件复用半径小。当前前景清晰且网络空闲后，可以沿最近移动方向预取 2 至 4 个相邻文件：

- 只预取与当前视锥扩张区域相交的文件。
- 不进入前景 `pending`。
- 网络并发最多 1 至 2。
- 内存压力、显卡压力或再次移动时立即停止。

这比扩大前景窗口到 64 以上更可控。

## 5.7 最后才考虑动态修改基础层级距离

在下载目标与引擎预算对齐之前，不建议先修改 `lodBaseDistance`，否则是在用降低画质掩盖过量下载。

如果完成前五项后，小尺度场景剩余的文件确实都是最终画质需要的，再增加网络自适应：

```text
移动中：
    临时降低 lodBaseDistance，使移动画面保持较粗层级

静止后：
    在 0.5–1 秒内恢复 quality mode 的配置值
    仅按中心优先逐级补细
```

注意当前规则中：

```text
增大 lodBaseDistance -> 更多区域使用细层
减小 lodBaseDistance -> 更早使用粗层
```

建议临时缩放范围限制为：

```text
0.5 × configuredBase
到
1.0 × configuredBase
```

只有在以下压力持续 300 毫秒以上时才降低：

- 预算目标 `pending > 12`
- 估算待下载点数超过 120 万
- 网络完成速率明显低于新增速率
- 单帧上传或显卡时间超过上限

恢复必须带迟滞，不能逐帧上下改变基础距离。

## 6. 推荐实施顺序

### 阶段 A：不改变最终画质

1. 下载目标改用预算后的 `nodeInfo.optimalLod`。
2. 相机移动后先更新引擎预算，再生成下载队列。
3. 小幅移动保留 `tracked`、`pinned` 和文件交集。
4. 爆发更新距离从 0 改为自适应非零值。
5. 增加暂停队列上限和存活时间。

预期直接改善 Wuhan / 南广场的 `pending` 峰值和请求尾部，同时不降低停止后的 quality mode 画质。

### 阶段 B：提高网络命中率

1. 文件级收益成本排序。
2. 空闲时方向性预取 2 至 4 个文件。
3. 最近视角文件使用有字节上限的短时缓存。

### 阶段 C：可选的移动中动态画质

1. 移动中暂时降低基础层级距离。
2. 网络压力高时延迟追细。
3. 静止后恢复配置值并完成最终收敛。

## 7. 静态验收指标

无需运行完整性能录制，也应先在调度日志中验证：

| 指标 | 目标 |
|---|---:|
| 小幅移动 `rawTargetUniqueFiles` | 仅用于诊断 |
| 小幅移动 `budgetTargetUniqueFiles` | 明显低于 raw 时证明此前存在过量下载 |
| `suppressedOverfetchFiles` | 文件不应随后立即被引擎请求 |
| 新旧前景文件复用率 | Wuhan / 南广场应提升 |
| 暂停队列长度 | 有硬上限，不随连续移动增长 |
| 停止后最终目标层级 | 与原 quality mode 一致 |
| 停止后最终活动点数 | 与允许误差内的基线一致 |

## 8. 最终判断

当前问题不是单纯的网络慢，也不是单纯的叶节点小，而是：

```text
小尺度
+ 固定米制层级门槛
+ 下载器忽略预算后的真实目标
+ 3 厘米移动触发
+ 每次移动清空复用状态
+ 爆发期间更新距离为 0
= 大量不稳定 pending 和网络尾部
```

最准确有效的第一步不是直接调大并发或直接改变画质，而是让下载器只追引擎预算后真正需要的文件，并让小幅移动复用上一视角的下载集合。
